## P-1: reported state versus contemporaneous execution

In upstream [cputime.c](https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git/tree/kernel/sched/cputime.c?h=v7.2.5), `thread_group_cputime` (306-359) sums exited-thread accounting and live-thread values. Its own comment explicitly leaves remote running tasks' pending scheduler runtime unrefreshed. A reader outside the target group does not trigger the current-group refresh. The 64-bit helper reads stored `sum_exec_runtime`; per-thread reads are not a simultaneous snapshot of every CPU. `CONFIG_VIRT_CPU_ACCOUNTING_GEN` also permits pending virtual time to be included in the split inputs (1031-1071); that does not establish fresh group scheduler-runtime totals.

The non-native adjusted path (739-828) serializes access to the group's persistent `signal->prev_cputime` pair. It retains the previous pair when sampled total runtime does not increase; otherwise it clamps the split to preserve component monotonicity and makes the sum equal the selected runtime. The returned pair is copied under that lock. The host configuration selects GEN; the proof below concerns this non-NATIVE branch, conditional on downstream equivalence and counter lifetime/arithmetic validity.

Two different targets therefore need separate treatment:

1. **Contemporaneous execution/runtime target.** Let X(t) mean accumulated physical execution, or the scheduler-runtime total with every running thread's pending time included at wall time t. The upstream group read does not establish that target at a single instant during the read. P-1's staleness concern is relevant here. Even a sum of individually coherent, monotone per-thread observations need not equal the simultaneous group state at any instant: discrete updates can make a mixed sum a value never held by the simultaneous aggregate. No numerical visibility lag, physical error or universal finite delta was proved. `CONFIG_HZ=1000` and a timer period alone provide none of those guarantees, especially without a proven tick/update/scheduling contract.
2. **Published adjusted reported-state target.** Define A_u(t), A_s(t) as the persistent group adjusted pair last published through that lock, including publications by other accounting consumers. For the inspected implementation, an individual stat invocation returns exactly that pair as it exists while the lock is held during the initial stat read. It may represent stale execution inputs and may itself advance publication. Those facts do not make it stale relative to this explicitly defined published state. The scalar X(t)=A_u(t)+A_s(t) is monotone on the supported lifetime, and the returned pair has a within-read instant for this target. This argument does not require a simultaneous snapshot of the upstream per-thread inputs.

The second interpretation is a supportable **conditional source proof**, not proof that the target is exact execution accrued during idle. It is consistent with the document's prospective reported-counter language only if root explicitly binds that target name and discloses publication/read dependence. Calling it fresh scheduler CPU, physical CPU, or the increment of an unquantized simultaneous group aggregate would silently change the estimand. Likewise, simply declaring the observed tick integer to be X would evade rather than establish the required model. Root has not selected any of these interpretations through this report.

Under the published-state interpretation and exact-build correspondence, the reviewer concern concerns the different physical/fresh-runtime target; it does not independently require a delayed bracket for a snapshot of published state. **For this actual build, neither interpretation's snapshot prerequisite is closed**, because implementation correspondence is still missing. P-1 is therefore not evidence for a chosen delta amendment, nor an automatic declaration that reported-counter snapshots are impossible.

## Conditional two-floor model

Upstream [time.c](https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git/tree/kernel/time/time.c?h=v7.2.5), lines 723-742, converts nonnegative nanoseconds by integer division when `NSEC_PER_SEC` is divisible by `USER_HZ`. With the inspected header candidate 100, the divisor is 10,000,000 ns. Together with the separate conversions in `array.c`, this gives, for the published adjusted pair,

`n(t) = floor(A_u(t)/10,000,000) + floor(A_s(t)/10,000,000)`.

Manual mathematical consequence: relative to `(A_u+A_s)/10,000,000`, the summed-counter truncation lies in `[0,2)` exported ticks; differencing endpoints gives an error in `(-2,2)`. This proves only quantization of this chosen pair. It adds no accounting-delay, physical-runtime or physical-accuracy bound. Publication's locked pair supplies the candidate snapshot point even though later formatting occurs outside the lock.

The actual-build model still needs the downstream implementations, constants/conversion branch, monotone pair lifetime and absence of relevant reset/overflow behavior bound to the role. Same start-time checks and an observed nondecreasing sequence cannot establish all of those semantics. Actual retained brackets and runtime tick-scale agreement are also unobserved. Consequently this investigation does not activate the document's conditional ±2 allowance for any role.

## Narrow wait4 and maxrss prerequisite inventory

Upstream [exit.c](https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git/tree/kernel/exit.c?h=v7.2.5), lines 1240-1298 and 1939-1949, passes `RUSAGE_BOTH` for the reaped child and accumulates accounted thread-group CPU plus previously reaped children into child-accounting fields; maxrss aggregation uses a maximum. This supports the harness's stated scope, conditionally: CLI thread group plus descendants incorporated through its waits, not arbitrary live, escaped or unobserved descendants and not a simultaneous sum of descendant RSS.

Upstream [sys.c](https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git/tree/kernel/sys.c?h=v7.2.5), lines 1846-1931, constructs the reported CPU components from adjusted group totals plus the relevant child totals. It converts each to a timeval. `time.c:465-475` truncates the nanosecond remainder to microseconds. This is not proof of microsecond physical accuracy or a justified `q_total`. If the target is exactly the returned timeval sum, that truncation defines part of its representation; treating the pre-timeval accounting total as the target instead must be explicit.

The helper source at `harness/phase7_spawn.c:223-236` calls `wait4`, forms double seconds from `tv_sec + tv_usec/1000000.0`, and emits each CPU value with six decimal places; maxrss uses `%ld`. Python parses the event with `json.loads`, retains it in a `SimpleNamespace`, multiplies CPU seconds by 1000 and integer maxrss by 1024 (`phase7.py:567`, `:1092`, `:1112-1113`). These are inspected source steps only. Binding the actual helper/runtime/ABI and a conservative conversion allowance requires a valid input range and rounding/conversion argument; six printed decimals alone do not prove exact recovery for all possible values. **No numerical `q_total` was derived or assigned.** Split attribution error must not be summed into total uncertainty.

`sys.c:1929` converts maxrss pages by `PAGE_SIZE/1024`, supporting Linux KiB for the upstream reported integer. The host configuration's 4 KiB page size is consistent. Integer JSON parsing and multiplication by 1024 have no representation error relative to that reported integer when the source/ABI/unit path is verified; this does not bound physical peak error. Upstream [mm.h](https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git/tree/include/linux/mm.h?h=v7.2.5), lines 3344-3352 and 3392-3442, uses per-CPU RSS counters and stored/current high-water information. The official [proc documentation](https://docs.kernel.org/filesystems/proc.html) also warns about asynchronous RSS accounting on SMP. Neither source supplies a physical-peak error bound here; this was not a complete audit of high-water updates. Exact-build RSS unit/accounting provenance is still pending, so no RSS gate is closed.
